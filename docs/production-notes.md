# What I would do differently in production

This repository is a reproducible demonstration on synthetic transactions, not a deployable fraud policy.

1. **Use event-time feature infrastructure.** This demo computes a graph in batch and serves a frozen training-cutoff snapshot. In production, an online feature store and an event stream would maintain account and counterparty statistics with explicit freshness, TTL, and recovery behavior. Online and training features would use the same code and event-time semantics.
2. **Wait for mature labels.** Chargebacks and investigations arrive late. The monitor queues retraining after drift, but a worker should start only when enough post-alert labels have matured. It should use a fresh chronological holdout and compare the candidate against the current champion on the same recent period before promotion.
3. **Prove incremental value from the graph.** PaySim's nearly unique sender IDs make graph features weak. I would collect repeat-actor signals such as device, IP, beneficial owner, and payment instrument links under a privacy policy; test whether graph features improve cost-aware recall after controlling for transaction features; and reject a more complex graph system if lift stays negligible.
4. **Use a scalable graph service.** NetworkX is appropriate for a bounded experiment, not a six-million-row live graph. I would move heavy graph aggregations to Spark or a graph database, use a compact online store for serving, and benchmark latency and memory at peak traffic.
5. **Calibrate decisions, not only rank scores.** PR-AUC is a ranking metric. A bank needs calibrated probabilities, monetary loss and investigator-capacity models, decision thresholds by segment, and separate review / decline policies. False positive impact needs a real cost estimate.
6. **Treat drift as evidence, not proof of model failure.** A feature shift can be caused by product changes, data outages, seasonality, or attack adaptation. I would add data-quality and delayed-performance monitors, segment alerts, control charts, ownership, and an incident playbook. A large KS statistic alone would not automatically deploy a new model.
7. **Harden serving and governance.** Add authentication, rate limiting, schema/version contracts, structured traces, feature and model provenance, audit logs, secrets management, access controls, CI security checks, rollback, and shadow/canary deployment. Human review would remain in the loop for material policy changes.
