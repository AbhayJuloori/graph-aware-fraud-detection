The graph idea failed. The pipeline caught it.

I built a fraud detector for 6.4 million mobile money transfers and tested a popular idea: that linking accounts into a network exposes fraud. A strict before and after test showed the network added nothing, so the simpler model shipped. Then I built the monitoring that says when it is time to retrain.

PaySim, a 25% label independent cohort, whole step chronological split. Logistic regression vs XGBoost vs XGBoost + 11 leakage safe NetworkX features. Graph lift was +0.0004 test PR-AUC against a 0.01 validation gate, so the transaction only model is the MLflow champion behind a FastAPI scorer with TreeSHAP reason codes, watched by Evidently and KS drift checks.

01 / The business problem

Fraud is 1 in 775 transfers. A model that always says "fine" is 99.9% accurate and useless.

Payment companies score every transfer in real time. Each alert costs an investigator's time, and every missed fraud costs real money. So the question is never "how accurate is the model". It is "how much fraud do we catch for the alerts we can afford to review", and "will it still work next month".

Positives are 0.13% of rows, so accuracy and ROC-AUC flatter any model. Candidates are ranked on PR-AUC and judged at an operating point: the threshold that keeps validation false positives at or below 1%, then applied unchanged to a later test window. A graph model must beat the transaction model by 0.01 validation PR-AUC to justify its serving cost.

02 / Inside the graph

Graph features may only know the past. Step through how they are built.

Every transfer links a sender to a receiver. Over time, that builds a network. The idea: if a receiver already took money from a fraudster, the next transfer to it is suspicious. The catch is time. A transfer may only be scored with what was known before it happened, or the model cheats. Click through the steps to watch it unfold.

This replays the exact rules of TemporalGraph: all rows in a step are scored against the graph as it stood at the end of the previous step, then that step's edges are added. Training labels update neighbor fraud rates after the step; validation and test labels never do. PageRank and weak components refresh every 168 steps.

Time step
scoring step 1

  1. 1

    Score with the past only

    Each transfer is scored using the network as it was before this hour began. Transfers in the same hour cannot see each other.

    row_features runs for every row in the step before add_edges_from, so siblings and the row itself are invisible.

  2. 2

    Then add the new links

    After scoring, the hour's transfers join the network for future hours.

    Directed edges sender→receiver; degree counts in plus out edges on the DiGraph.

  3. 3

    Learn labels from training only

    Fraud outcomes teach the network which accounts are risky, but only for the training period. Later outcomes stay hidden, as they would in real life.

    learn_labels=True only in the training window; sender and receiver fraud rates are counts over earlier labeled rows.

  4. 4

    Refresh the slow features weekly

    Expensive network scores are recomputed once a simulated week.

    PageRank (α 0.85) and weakly connected components every 168 steps; the serving copy is frozen at the training cutoff.

  5. 5

    Most transfers look like step 4

    Two brand new accounts, no history, every network feature zero. In PaySim, that is nearly every sender.

    On held-out rows, sender degree is non-zero 0.1% of the time; shared counterparties and ring flags are never non-zero.

CASE 01 Confirmed

Transaction features alone rank fraud almost perfectly.

0.978test PR-AUC

The tree model (XGBoost) puts nearly every fraud above nearly every normal transfer. The simple straight line model (logistic regression) cannot: it misses the "if transfer AND account emptied" combinations that trees learn easily.

CASE 03 Hypothesis rejected

Graph features never earned their keep.

+0.0004graph lift

I tested the network idea on three separate slices of data. The result flipped between a tiny gain and a tiny loss each time. That is noise, not a signal. A network service is expensive to run in production, so the rule was set high: it must clearly win, or the simpler model ships.

Graph lift (graph minus transaction XGBoost PR-AUC) by cohort. E3 showed +0.0012 on validation and −0.0038 on test, which is why the absolute 0.01 validation gate exists. E4 is a disjoint row cohort and is the published confirmation. Sign flips with fewer than 210 validation positives mean no demonstrated lift.

CASE 04 Root cause

Why: there is no network to find. 99.85% of senders show up once.

0%rows with a shared contact

Network features work when the same people keep showing up. In this data, almost every sender appears exactly once, and fraud receivers are almost never reused. So the "network" is mostly disconnected pairs. The only feature that fires often is "how many transfers this receiver got before", and it does not separate fraud.

Share of held-out rows where each graph feature is non-zero. Sender side features are dead (0.1%); triangle closure and shared counterparty features are exactly zero; receiver degree is non-zero on 42% of rows but mean SHAP is small. Across the full dataset, 0.5% of fraud receivers are reused and 0.2% ever send money, so mule chains cannot be traced.

CASE 05 Explained

One pattern explains most fraud: the account gets emptied.

97.8%of fraud empties the account

Almost every fraud moves the sender's entire balance in one go. Normal customers almost never do that. The model's explanations, built with SHAP, show it leaning on exactly that ratio. Every alert from the API comes with its top three reasons, so an investigator sees why. Pick a case below.

amount / (oldbalanceOrg + 1) has mean |SHAP| 6.4 log odds, about 6× the next feature. Among legitimate TRANSFER and CASH_OUT rows, only 0.0002% drain the balance exactly. This is a generator artifact of PaySim's fraud agent, which is why scores this high do not transfer to live data. The waterfall shows the API's real reason codes: base log odds, plus the top three TreeSHAP contributions, then the remaining features.

CASE 06 Alert rule

The drift alarm fires when amounts rise 1.5× or fall to 0.75×.

0.288amount KS at 3×

Models go stale when the world changes. This replay takes next month's transfers and scales every amount, as if prices or customer behavior shifted. The monitor compares them with last month and raises an alarm when the difference is big enough. It also shows the cost: at 3× amounts, investigator alerts quadruple.

Reference = validation window; current = later test window, amounts scaled then rescored through the champion. Two sample KS on 20,000 row samples; alert if statistic ≥ 0.10 and p < 0.01. The natural replay is healthy (0.033 / 0.010). An alert writes a retrain request that waits for mature labels instead of retraining blindly.

POST MORTEM Guardrail added

Two traps I would have walked into without the guardrails.

1. The lucky win. On my first big slice of data, the network model beat the simple one on the practice exam (validation). Under the old "highest score wins" rule, it was promoted. Then it lost on the real exam (test). A tiny win on a few hundred fraud cases is luck. I added a minimum winning margin and reran on fresh rows, keeping the failed attempt in the record.

1. Selection noise. E3 registered the graph model on a +0.0012 validation edge, then lost 0.0038 on test. With 168 validation positives, PR-AUC differences of 10⁻³ are inside sampling noise. The fix: a prespecified absolute 0.01 gate, then a disjoint E4 cohort for confirmation. E3 stays in the experiment log as exploratory.

2. The jumpy alarm. Checked over the whole month, the natural data is healthy. Checked one day at a time, the same alarm fires on 5 of 17 days. Two of those days have almost no transfers, so a handful of fraud rows swing the numbers. A real monitor needs a minimum volume and a threshold tuned to its window size, or investigators learn to ignore it.

2. Window sensitivity. Daily KS (5,000 row samples) crosses 0.10 on days 3, 4, 11, 16 and 17 of the natural replay. Days 16 and 17 hold 492 and 17 rows where PaySim's tail is mostly fraud (score KS 0.999). Production alerting needs minimum volume guards, calibrated per window thresholds, and seasonality aware references.

05 / Why trust it

Built so it cannot cheat by peeking at the future.

Fraud models fail quietly when information from after the transaction leaks into training. These are the controls that keep the results honest.

No after the fact fields

PaySim includes the balance after each transfer and a built in fraud flag. Both reveal the answer, so neither is ever used.

newbalanceOrig, newbalanceDest and isFlaggedFraud are excluded at load time; a unit test proves changing them cannot change features.

Split by time, not at random

The model learns from the first 60% of the month, is tuned on the next 20%, and is graded on the final 20%, the way it would be used.

Whole steps go to one window (train ≤ 281, validation 282 to 355, test > 355), so no hour is split across windows.

Fresh rows to confirm

The final result was rerun on a completely separate set of transfers, so the decision is not tuned to one lucky sample.

Seeded uniform draws; window [0.25, 0.50) is disjoint from E3's [0, 0.25). Sampling is independent of labels.

Failures kept on record

The attempt where the network model got lucky is documented, not deleted. So is the rule change it caused.

The experiment log keeps E1 to E4 and M1/M2. The 0.01 gate was adopted after E3 and is disclosed as such; E4 is the only confirmatory run.

Bit for bit reproducible

Rerunning the training from scratch gives the same numbers to six decimal places.

Fixed seeds through sampling, XGBoost, and SHAP sampling; a rerun reproduced every PR-AUC in results.json exactly.

Tested on every change

Automated tests check the time rules, the alarm, and the retrain queue on every commit.

pytest + ruff in GitHub Actions on synthetic fixtures: same step isolation, label masking, unsorted input alignment, disjoint sampling, alert queueing.

Honest limits

  • PaySim is synthetic and easy. Its fraud agent drains accounts in a way real fraudsters rarely make so obvious. A 0.98 PR-AUC here says nothing about live fraud rates.
  • The graph verdict is about this data. Real payment networks have repeat customers, shared devices and mule accounts, where graph features often do help. The project shows how to test that claim, not that graphs never work.
  • The threshold slider reads the test window. It illustrates the tradeoff; a real policy would set it on validation with actual review and loss costs.
  • NetworkX is a demo engine. Production would use a streaming feature store and a graph service with freshness guarantees. See production notes.
